# `magecommand di verify`: reading the report

`magecommand di verify --archive <php-output> --output <magecommand-output>` compares a
magecommand compile with a reference `generated/` tree, usually one produced by
`bin/magento setup:di:compile`. It sorts every difference into one of three buckets:

- **Unexplained.** The difference matches none of the patterns below. These are the ones
  to investigate, and the only ones `--fail-on-diff` fails on. The report lists them first,
  split by where they live:
  - **DI config** (`generated/metadata/`): the compiled object-manager config, i.e. the
    per-area `<area>.php` files, `interception.php` and the `*plugin-list.php` caches.
    A difference here changes how Magento wires objects.
  - **Generated code** (`generated/code/`): interceptors, proxies, factories and the
    other generated classes. A difference here changes the PHP that runs.

  Each changed file is shown with its **first divergence**, one line from each side,
  after the same normalization the classifiers apply. So that line is a real
  difference, not an entry that one of the patterns below already explains.
- **Explained.** The difference is known and expected. Each group links to its section
  below.
- **Warning.** Shown, but neither explained nor a failure:
  [filename casing](#filename-casing) on macOS, and
  [constructor arguments left to runtime reflection](#runtime-resolved-arguments).

magecommand targets **Mage-OS 3.1.0 / Magento 2.4.9**. Most explained differences come from
comparing against an archive built by an older Magento (2.4.8 or earlier, see
[the disabled-module groups](#disabled-module-artifacts)), or on a different machine.

## Investigating an unexplained difference

- `--show-residual <path>` (e.g. `metadata/global.php`) prints the full context around
  the first divergence of one changed metadata file, with the same normalization applied.
- `--json` prints the raw compare report and the classification, including every file
  in every group.
- `--no-explain` turns classification off and lists every byte-level difference.
- Compile from empty, the way CI does. Building the reference into `generated/_code`
  first makes magecommand scan the reference as its class universe, which hides some
  bugs.
- **Check the archive's age before blaming the output.** A reference compile is a
  snapshot of the codebase at the moment it ran, so one left lying around drifts: a
  `composer update` that patches a constructor makes every interceptor for that class
  differ, and moving the checkout changes the absolute paths the ClassesScanner exclude
  regex bakes in, which lands as a change in every `metadata/<area>.php`. Both look like
  magecommand bugs and are not. If the first divergence is a path prefix, or a
  constructor parameter that the current source really does declare, regenerate the
  archive.

A divergence that stays unexplained on a store whose Magento matches magecommand's
target is a magecommand bug. Report it with the first-divergence lines, or the
`--show-residual` output.

## Plugin-list scope order

*DI config.* The plugin-list cache filename encodes the set of config scopes it was
compiled from. magecommand sorts the scope names alphabetically
(`adminhtml|global|primary`); Magento 2.4.8 and earlier write them in whatever order the
generator happened to build its scope scheme (`primary|global|adminhtml`).

The sorting comes from [magento/magento2#40408](https://github.com/magento/magento2/pull/40408)
by **Jakub Winkler** (`jakwinkler`), which fixes
[magento/magento2#40407](https://github.com/magento/magento2/issues/40407) — *"Plugin
list metadata files generated by `setup:di:compile` are never used at runtime due to
cache ID mismatch"*. The reader and the writer build the same cache id by two different
rules:

- `PluginList::_loadScopedData()` moves the current scope to the **end** of
  `scopePriorityScheme` before joining it. With the scheme `app/etc/di.xml` configures,
  `[primary, global]`, a load in the `primary` scope therefore asks for
  `global|primary|plugin-list`.
- `PluginListGenerator::write()` only **appends** a scope it has not already got, so the
  compile writes that same file as `primary|global|plugin-list`.

The two never meet, and the reorder persists on the object: once a `primary`-scope load
has missed, every later area asks for `global|primary|<area>` while the compile wrote
`primary|global|<area>`. `ConfigLoader\Compiled::load()` is an unguarded `include()`, so
each miss emits a PHP warning, falls through to the cache backend, and ends in
regenerating the whole plugin list in-process — the 1–2 s first request after a cache
flush that the issue reports. Sorting both sides fixes it: one scope *set* maps to one
filename however the scopes are ordered.

**Status.** Mage-OS merged the patch — `sort($sortedScheme)` sits in
`PluginListGenerator::write()`, in `PluginList::_loadScopedData()` and in the setup
operation on `mageos-magento2` main, with Winkler's comments verbatim. Adobe did not:
#40408 and the follow-up [#40499](https://github.com/magento/magento2/pull/40499) were
both closed unmerged, and #40407 is still open. So on an Adobe-lineage store the
compiled plugin lists are not the ones its runtime looks for — Adobe's own as much as
magecommand's. magecommand follows Mage-OS, which is the behaviour that makes the files
usable at all. The one case where the divergence costs something is a process whose
first plugin-list load is an area rather than `primary`: an unsorted name would hit
there, a sorted one cannot.

The report pairs each renamed file with its counterpart, and claims a pair only when
the two files carry the same content — byte-identical, or equal once the key order is
canonicalized, since `PluginList` reads those sections by key and never iterates them
(see [ordering only](#ordering-only)). A pair whose contents genuinely differ is **not**
claimed. It is still one file, so it is reported as one unexplained `changed` entry
under the archive's name, with the name magecommand wrote it under alongside:

```
changed  metadata/primary|global|webapi_rest|plugin-list.php
           written as global|primary|webapi_rest|plugin-list.php (expected: magecommand sorts the scope names)
           3 type(s) with differing entries:
             changed  Magento\Sales\Model\ResourceModel\Order\Collection\AbstractCollection
             missing  Magento\InventorySalesApi\Api\IsProductSalableInterface  (disabled module Magento_InventorySalesApi)
             changed  Amasty\ShopbySeo\Controller\Router  (disabled module Amasty_ShopbySeo)
           - archive: 'Magento\\Sales\\…\\AbstractCollection' =>
           + output:  'Magento\\Sales\\…\\AbstractCollection' => NULL,
```

The name is accounted for; the content is a second problem, unrelated to it, and
`--fail-on-diff` fails on it. The report names every type whose entry differs (the
order of entries is ignored: `PluginList` only looks them up by key), and tags the
types of modules disabled in `app/etc/config.php`. Those tags matter: plugins that
reach into a disabled module — an enabled module plugging a disabled module's class,
or a disabled module's interface still on a class hierarchy — are the interactions
magecommand most often gets wrong, and they are bugs to report, not expected
differences. Better still, don't ship disabled modules: `composer remove` them, or
`replace` Magento's own (MSI). The `-`/`+` lines are the first real content difference
outside those disabled-module entries. (`--json` lists these pairs as
`classified.renamed_changed`.)

Compare the file sizes first when one shows up. A per-area list that is a fraction of
the archive's is missing the global plugin baseline every area is reset to — the shape
of a bug fixed in #129, where only the first area compiled kept it.

## Disabled-module artifacts

*Generated code.* Interceptors, proxies and factories for classes in modules that are
disabled in `app/etc/config.php`. Since Magento 2.4.9, `setup:di:compile` compiles only
enabled modules, and magecommand does the same. An archive from 2.4.8 or earlier compiled
every module on disk, whether it was enabled or not. Leaving them out is the
improvement: no code gets generated that can never run.

A module counts as disabled here — and in the three sections below — in either of the two
shapes `config.php` can express: `'Vendor_Module' => 0`, **or no entry at all**. Deleting
the line while the package stays installed is the ordinary way to switch a module off, so
the two have to mean the same thing; `magequery modules --check` lists the second kind as
`unregistered`.

## Disabled-module metadata

*DI config.* Metadata files (`<area>.php`, `interception.php`) that are byte-identical once
the archive's entries for classes in disabled modules are removed. This is the same 2.4.9
behavior as above, for the compiled config. An entry is only removed when the output does
not have it: a 2.4.9 compile emits nothing for a disabled module, so if the output carries
such a key, its value is compared like any other.

## Disabled-module reachable types

*DI config.* Types named after an **enabled** module that nothing in the enabled
codebase pulls into the compile. Each one is declared by a disabled module, or is a
parent class or implemented interface of a class in one. A compile that includes every
module drags those interfaces into the interception walk; a 2.4.9 compile does not. The
classic case is an interface in a core module whose only implementations ship in a
disabled payment module. The disabled modules' own source verifies this, with one PHP
header parse per file.

## Disabled-module reachable artifacts

*Generated code.* The file-level twin of the previous section. Some generated artifacts,
usually factories, are named after an enabled module, but the only constructors that
type-hint them live in disabled modules. A compile that reads every module emits them;
since 2.4.9, nothing left in the codebase asks for them.

## Outside scan paths

*Both trees.* Classes in a composer package that registers itself as a module in
`registration.php` but ships no `etc/module.xml` and is not in `app/etc/config.php`. Such a
package is not an enabled module. Older compilers walk the ComponentRegistrar paths
directly and compile it anyway; magecommand discovers modules through `module.xml` plus
the enabled list.

This is matched by location, not by name: each class resolves to a real file that lies
under none of the compile's scan roots (enabled module directories, the framework
library paths, `setup/src`). A missing framework or module entry therefore still fails.

**Worth a look:** if a package listed here is supposed to be live, it isn't. It needs a
`module.xml` and an entry in `config.php`.

## Extra metadata

*DI config.* The output equals the archive once these specific additions are set aside:

- the `nonLazyTypes` section and its `NonLazyTypes` step in `ModificationChain`, from the
  lazy-proxy compiler pass of 2.4.9 / PHP 8.4. This only applies when the archive has no
  such section; an archive that ran the pass must match it exactly.
- `interception.php` rows that say `false` (no plugins) for a type the archive has no row
  for. Without a row, Magento works that out at runtime. If `false` were wrong, the type's
  interceptor and plugin-list entries would be missing too, and those stay flagged.

Any other addition keeps the file flagged: an extra plugin, preference or `arguments` row
changes what runs, and an argument inserted into an existing row shifts every later one,
because Magento passes them by position.

## Class-scanner exclude regex

*DI config.* The ClassesScanner exclusion regex
(`#^(?:…/vendor/<pkg>…|…/app/code/<Vendor>/<Module>…)/Test#` and its `/tests#` sibling) lists
every enabled module directory. An archive compiled from a different module set lists
different members, in a different order. The file matches once that regex is
canonicalized on both sides, disabled-module entries are removed and the
[extra-metadata](#extra-metadata) additions are set aside. Any other changed or added value
keeps the file flagged.

## Setup area config

*DI config.* The output's `arguments` have rows for the setup application's own classes
(`Magento\Setup\…`, files under `setup/src`) that the archive doesn't. Since Magento 2.4.8
([magento/magento2#33161](https://github.com/magento/magento2/pull/33161)),
`setup:di:compile` passes `setup/src` to the step that writes the per-area DI config. Before
that it scanned `setup/src` only for code generation, so a 2.4.7-or-older reference has no
rows for these classes. magecommand targets 2.4.9 and writes them.

Explained only when both checks hold:

- the class resolves to a file under `setup/src` (a generated factory, through the class it
  is generated for), and
- the checkout's own `setup/src/Magento/Setup/Console/Command/DiCompileCommand.php` leaves
  `setup` out of its `AREA_CONFIG_GENERATOR` paths.

On a 2.4.8+ checkout, and when verify has no checkout to read, nothing is explained, so a
setup row missing from a current reference still fails. The rule assumes the archive was
compiled from the checkout passed as `--root`.

## Filename casing

*Generated code. A warning, on macOS only.* Paths that differ only in letter case
(`Tierprice` vs `TierPrice`). A case-insensitive filesystem can't hold both spellings, so
which one each tree kept can depend on creation order, and the two can't be compared there.
On macOS these are listed as a warning and don't fail the verify. Everywhere else they stay
unexplained: on Linux the two spellings are two different files, and the autoloader asks for
one exact spelling.

## Generator version formatting

*Generated code.* Both files are parsed and compared as structure: the class declaration,
every method signature with its resolved types and defaults, and every method body as
tokens. Formatting, docblocks and method order therefore never count. On top of that,
exactly these changes Magento's code generator made between versions are allowed:

- explicit nullable defaults: a nullable parameter with no default in the archive and
  `= null` in the output (the PHP 8.4-compatible form)
- in proxies only, the laziness hardening: `__clone` and `_resetState` may each be the old
  or the new template body (the new one has null guards, so cloning or resetting an unused
  proxy no longer instantiates it), and the output may add the template's `__debugInfo`

Anything else is a difference. That includes a default that the output *drops*, which PHP
rejects as an incompatible override. These differences disappear on a 2.4.9 store.

## Obfuscated vendor source

**Not an expected difference.** Versions up to 0.21.0 listed it here, and that was a bug.

The constructor chain of these classes runs through vendor source whose class declaration
exists only inside an `eval()` of encrypted code. magecommand never executes PHP, so it
couldn't see the constructor, and versions up to 0.21.0 wrote `NULL` as the class's
`arguments` entry. The same happened for a parent that is a PHP built-in with no modelled
signature (`DateInterval`, `DateTimeZone`, `SoapClient`, `IteratorIterator`), and for a
constructor default it can't evaluate. Those versions assumed Magento falls back to
runtime reflection for a `NULL` entry. It doesn't:
`ObjectManager\Config\Compiled::getArguments()` turns a present `NULL` into `[]`, and the
compiled factory answers `[]` with `new $type()`. Only a key that is *absent* from
`arguments` gets runtime reflection. The result is an `ArgumentCountError` the first time
the class is built (or, if every parameter is optional, every argument di.xml configures
is silently dropped).

`di verify` now reports any `arguments` entry that is `NULL` (or an empty row) in the
output while the archive has a row as **unexplained**, whatever else the file matches.
The report leads with these classes and names the `eval()`'d file behind each one when it
can find it.

`di compile` now leaves such a class out of `arguments` altogether, which is what runtime
reflection needs. See [the next section](#runtime-resolved-arguments) for how verify
reports that.

## Runtime-resolved arguments

*DI config. A warning, or unexplained when di.xml configures the class.* The archive has
a constructor row for a class, and the output has no `arguments` key for it at all. That's
what `di compile` writes when it can't resolve a constructor statically (see
[above](#obfuscated-vendor-source)). An absent key makes
`ObjectManager\Config\Compiled::getArguments()` return null, so the compiled factory
reflects the real constructor at runtime and autowires it. The class works, at the cost of
one reflection on first use instead of a cached row.

The runtime branch never reads di.xml `<argument>` configuration, which exists only in the
compiled row. So verify checks the merged di.xml of every area, for the class, the types it
inherits configuration from, and (for a virtual type) its base chain:

- **Nothing configured:** the class is listed as a warning, and a file whose only
  difference is such keys doesn't fail the verify.
- **Arguments configured:** **unexplained.** The class builds, but without its di.xml
  arguments. The report leads with these classes, and `di compile` names them on stderr
  as well.
- **No checkout** (verify can't open `--root`): unexplained, since nothing can be proven.

## Ordering only

*Both trees.* Same content in a different order. This is never counted as unexplained;
pass `--strict-ordering` to treat it as `changed`.

- **Interceptor method order.** PHP's `getMethods()` order, which the interceptor
  generator follows, differs between PHP versions (8.4 vs 8.5) for classes that use
  traits. Method order in a PHP class has no effect on behavior.
- **Plugin-list key order.** `PluginList` reads the `_data`, `_inherited` and `_processed`
  sections only by key (`isset`, `array_key_exists`, `[$type][$code]`) and never iterates
  them, so array key order can't be observed.
